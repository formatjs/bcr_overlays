# Hermeticbuild comparison

Review: 2026-11-05. Source snapshots pinned below. Code inspection; no upstream builds or performance benchmarks run.

## Rust migration

The Chromium import now uses `rules_rs@0.2.1` and upstream
`nightly/2025-09-25`, with matching target standard libraries. The full imported
Rust crate set and native font/PNG runtime test pass. Five compile/link probes
produced the expected ELF, Mach-O and PE architectures; Windows uses MSVC.
A local patched-rules_rust fix routes MSVC linker arguments to `lld-link`.
The exact Chromium compiler was a conservative starting point, not a requirement
for this validated crate set. Full browser builds with the replacement remain
unverified.

## Fix validation

- Remote execution now selects `//platforms:buildbuddy_linux_amd64`, using Node's pinned image digest and Chromium's GNU 2.31 constraint. Hosted rerun still required to validate the worker.
- Generator, runtime bundle and archive actions invoke pinned Python directly. Empty-PATH Linux sandbox integration passed all three actions. Other Python CLI tools use rules_python's script bootstrap; those still require the execution platform's shell.
- Locale generator inputs fell from 35,245 to 7,467. Its 707,553-byte output stayed identical. DevTools build tools now select installed runtime package closures instead of the complete npm tree. TypeScript, esbuild, CSS and Rollup replays passed with roughly 70% fewer inputs and all 358 outputs byte-identical.
- Archives normalize gzip/tar times, ownership and modes. Repacking after mtime/permission changes gives identical bytes. Packaging is a cached Bazel action; build output discovery reads BEP from the same invocation.
- Real Chromium artifact passed relocation, HTTP and both rendering smoke tests with zero changed pixels. Full browser cross-platform ports remain separate unfinished work.

Findings below describe the reviewed baseline, before these fixes.

## Adopt first

**Pin the remote execution runtime first.** The first inspected Linux BuildBuddy invocation failed while running Chromium's Node tool: `GLIBC_2.28' not found`, plus missing 2.25/2.27 symbols. Workflow `container_image: ubuntu-24.04` selects the workflow VM, not necessarily the remote action worker. Chromium registers host/LLVM execution platforms without a pinned worker image. Node defines a separate `rbe_platform` with digest-pinned `buildpack-deps`, OS/architecture properties and an explicit extra execution platform. Adopt that separation, or make generator runtimes self-contained, then rerun the failed action. This diagnoses this invocation; it does not explain every platform failure. [Failed invocation](https://formatjs.buildbuddy.io/invocation/3d9a4691-fa94-47d0-ad66-fbff4e9ce7d0), [Chromium platforms](../MODULE.bazel#L98), [Node remote platform](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/BUILD.bazel#L11), [platform selection](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.bazelrc#L53).

1. **Make archives reproducible Bazel outputs.** Chromium packaging currently runs outside Bazel with `tarfile.open(..., 'w:gz')` and `add()`; tar records filesystem ownership/timestamps, gzip records creation time. Same browser/revision can produce different archives. Node.js constructs release archives through Bazel actions, normalizes ownership, modes, ordering and timestamps, then tests archive metadata and executes relocated Node/npm/npx. Adopt normalized metadata plus byte-for-byte repack checks; cache packaging as an action. [Chromium packaging](../tools/ci/chromium.py), [Node archive rules](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/nodejs/private/release_archive.bzl#L429), [normalizer](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/nodejs/private/release_mtree.c#L181), [archive tests](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/tests/release/release_archive_test.py#L25).

2. **Separate exec tools from target artifacts, then test resolution.** Node.js generator executables use `cfg = "exec"`; its consumer test resolves the Node execution toolchain and fails unless it supplies a hermetic binary. Its Rust declaration includes all six target standard libraries. Chromium's five `with_cfg` wrappers are useful, but do not prove imported generators, Rust libraries, or platform-specific browser graphs work. Add consumer tests that cross-build a target while executing its generators on Linux. Keep Chromium's exact Rust compiler requirement; Node's stable 1.92.0 toolchain is not an automatic replacement. [Generator](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/nodejs/private/node_javascript.bzl#L55), [execution test](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/tests/integration/execution_toolchain_check.bzl#L3), [Rust matrix](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/MODULE.bazel#L43).

3. **Enforce clean execution and locked dependency resolution.** Node CI builds/tests with `--lockfile_mode=error`; its Bazel configuration disables sandbox network access, requests strict action environments and disables host C++/Apple toolchain discovery. Chromium should validate these settings against actual native actions, then enforce them in CI. Node still has `run_shell` actions, so its code does not establish a completely shell-free build. [CI](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.github/workflows/ci.yml#L23), [configuration](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.bazelrc#L7), [shell action](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/nodejs/private/node_javascript.bzl#L26).

**Python bootstrap is a shared weakness.** Chromium's generated Python action launcher uses `#!/usr/bin/env python3`. Node also declares rules_python 1.8.0 with a hermetic 3.11 toolchain but no bootstrap override; that ruleset defaults to `system_python`. This is configuration evidence, not a reproduced Node failure. `--@rules_python//python/config_settings:bootstrap_impl=script` removes the system-Python bootstrap requirement on supported platforms, but typically retains a shell dependency; Windows forces the system bootstrap in these releases. For shell-free execution, invoke the declared interpreter directly or generate a native hermetic-launcher around that interpreter, including script/runtime runfiles. Wrapping the unchanged Python-shebang executable preserves its leak. [Node Python declaration](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/MODULE.bazel#L16), [rules_python default](https://github.com/bazel-contrib/rules_python/blob/1.8.0/python/config_settings/BUILD.bazel#L93), [bootstrap contract](https://github.com/bazel-contrib/rules_python/blob/1.9.0/docs/api/rules_python/python/config_settings/index.md#L348), [native launcher API](https://github.com/hermeticbuild/hermetic-launcher/blob/b0d103f65a4d2a14c6407d2ffb7208aa36cd745f/launcher/private/rules/lib.bzl#L45).

## Build performance

**Measure action inputs before raising concurrency.** linux.bzl selects source input groups for object actions and retains File-backed directory arguments for Bazel path mapping. Its action wrapper explicitly advertises `supports-path-mapping`. Those are useful patterns for Chromium's large generated action graph: compare action input counts/bytes, analysis memory, upload time, cache hits and one-file rebuild invalidation. Path mapping requires auditing every path-bearing argument/environment/output; adding its flag alone is insufficient. [Input selection](https://github.com/hermeticbuild/linux.bzl/blob/002b89d400daceae6652b4881a9882db24d615d1/internal/linux_objects.bzl#L1145), [compile action](https://github.com/hermeticbuild/linux.bzl/blob/002b89d400daceae6652b4881a9882db24d615d1/internal/linux_objects.bzl#L6392), [path mapping](https://github.com/hermeticbuild/linux.bzl/blob/002b89d400daceae6652b4881a9882db24d615d1/internal/path_mapping.bzl#L18).

**Tune remote execution separately from local builds.** Node enables remote cache compression, top-level downloads, explicit execution platforms, remote timeouts/keepalives and up to 800 jobs; its CI overrides concurrency to 64. Chromium already uses 64 jobs/top-level downloads. Benchmark compression and upload/download behavior before copying more flags. Chromium's `--discard_analysis_cache`, `--notrack_incremental_state`, `--nokeep_state_after_build` favor memory over warm local rebuilds; keep that tradeoff scoped to CI/full-browser builds. [Node configuration](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.bazelrc#L45), [Chromium configuration](../.bazelrc).

**Use strict isolation as a test lane.** actiond documents remote-only execution with local fallback/upload disabled. This can expose accidental host dependencies missed by permissive local execution. Its README's 20–30% LLVM smoke speedup is an upstream claim, not Chromium evidence; it also allows explicit libc runtime mounts, so isolation alone does not mean every runtime is an action input. [actiond setup and runtime](https://github.com/hermeticbuild/actiond/blob/5a0335c607a367f02f2dfcea380799e3bcbac767/README.md#L82).

## Runtime performance and portability

Node CI explicitly builds `opt`/`-O3` and executes both Windows artifacts natively, plus Linux/macOS tests. That is stronger validation than platform declarations, but not published performance parity. Chromium needs equivalent successful full browser runs before claiming five-platform support. Our rendering smoke adds coverage Node does not need. [Release settings](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.bazelrc#L23), [native CI](https://github.com/hermeticbuild/nodejs/blob/a3fe5d39729df187d781271e0605d52955c4b484/.github/workflows/ci.yml#L106).

Chromium already retains GN's C++ `-O2` and Rust `-Copt-level=3`; `fastbuild` output paths do not establish an unoptimized browser. Rust debug assertions also remain enabled. Benchmark startup, JS/rendering throughput and memory before changing those settings or ABI-sensitive libc++ hardening. [C++ flags](../overlays/chromium/bcr/overlay/native/browser_sources.bzl#L66), [Rust flags](../overlays/chromium/bcr/overlay/native/rust/crates.bzl#L22), [Rust toolchain](../overlays/chromium/bcr/overlay/native/rust/BUILD.bazel#L33).

Hermetic LLVM implements deterministic compile settings and source-backed compiler bootstrap ThinLTO/FDO. Those optimize the compiler; they do not enable Chromium application PGO/LTO. MSVC support has explicit limitations around FDO, sanitizers and coverage. Establish optimized browser baselines, then measure startup, rendering/JS throughput, binary size and build cost before selecting ThinLTO/PGO. [Deterministic flags](https://github.com/hermeticbuild/hermetic-llvm/blob/c04d527ee4cc2247c82232c1927984714ddb2146/toolchain/args/BUILD.bazel#L325), [bootstrap transition](https://github.com/hermeticbuild/hermetic-llvm/blob/c04d527ee4cc2247c82232c1927984714ddb2146/toolchain/bootstrap/bootstrap_binary.bzl#L22), [MSVC limits](https://github.com/hermeticbuild/hermetic-llvm/blob/c04d527ee4cc2247c82232c1927984714ddb2146/README.md#L314).

hermetic-launcher supplies target-specific native wrappers using separate template/finalizer toolchains and merges executable runfiles. Consider it where Chromium generators currently need portable executable wrappers; replacing a wrapper alone does not fix undeclared tools or environment. rules_rs likewise distinguishes execution toolchains from target triples and supports custom compilers; any adoption must preserve Chromium's exact compiler/stdlib compatibility. [Launcher rule](https://github.com/hermeticbuild/hermetic-launcher/blob/b0d103f65a4d2a14c6407d2ffb7208aa36cd745f/launcher/private/rules/launcher_binary.bzl#L3), [custom Rust compiler](https://github.com/hermeticbuild/rules_rs/blob/52ecddc9d35b72ca78455199cbed099afd13997e/README.md#L291).

## Local evidence

- The generated `python_action_runner` starts with `#!/usr/bin/env python3`. Running that existing launcher with an empty `PATH` failed with exit 127 before reaching the pinned interpreter. This reproduces a host-Python dependency despite the declared Python 3.11 toolchain. Native generator and bundle runners use ordinary `py_binary` declarations without a bootstrap override. Node shares the configuration weakness described above; it is not evidence of an advantage over Node. [Runner declarations](../overlays/chromium/bcr/overlay/native/BUILD.bazel#L64).
- Existing build output contains 7,700 Python action manifests: median 148 input entries, maximum 35,245; 1,345 exceed 10,000. Combined input entries total 44,494,141. These are output-tree measurements, not a fresh current-graph `aquery`. The maximum target still exists in `browser_sources.bzl`. `python_action.py` copies every non-tool input with `copy2`; the largest manifest symlinks only two tool entries. Reduce transitive input propagation and repeated staging; measure bytes and time before changing semantics. [Staging](../overlays/chromium/bcr/overlay/native/python_action.py#L35), [largest target](../overlays/chromium/bcr/overlay/native/browser_sources.bzl#L876490).
- Repacking one unchanged tiny valid bundle twice, 1.2 seconds apart, produced different SHA256 values. Manifest mtime changed; archive nonreproducibility is reproduced, not just inferred.
- A previous warm full-browser build configured 379,666 targets, reported 162,038 action cache hits, and took 113.235 seconds with a 9.34-second critical path. This establishes substantial work outside the executed critical path; it does not isolate analysis from cache checking or measure cold/RBE performance. Evidence: `/tmp/chromium-browser-final-runtime-build.log`.
- CI builds with memory-saving flags that discard analysis state, then runs `cquery` with the same configuration. That forces another analysis to find the bundle. Keep the memory tradeoff available, but move packaging into Bazel or read output paths from the first build's BEP rather than analyzing again. [Memory flags](../.bazelrc#L8), [build followed by cquery](../tools/ci/chromium.py#L115), [Bazel flag semantics](https://bazel.build/versions/7.7.0/advanced/performance/memory).

Priorities: fix remote worker/runtime mismatch; deterministic archives; successful platform builds/native smoke; strict dependency/environment checks; action-input and incremental profiling; browser optimization experiments.
